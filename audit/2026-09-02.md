# Repository audit -- 2026-09-02

Head audited: `618596a`. Environment: a Linux coding session, so everything here
is code reading plus the headless Lua suite on the vendored 5.4.7 engine. The
Swift build, the UI tests, the live feature matrix and profiling need a Mac;
they are listed at the end with what each should settle.

Scope was chosen to avoid re-checking what the repo already machine-checks.
Capability declarations (both directions), the feature require allowlist, i18n
parity, LuaLS types at Error level, the subprocess-site roster, README catalog
sync and the business-content hook are all gated in CI already. This looked at
what no guard covers: the trust boundaries, error containment, teardown, the
docs' factual claims, and the shape of the test coverage itself.

## Verdict

**Corrected 2026-09-02, second pass.** The first version of this report said "no
S1 or S2 finding". That verdict was true of what had been READ, and the reading
was incomplete: three of the six parallel readers died on a rate limit mid-run
and were never replaced before the report was written, so the pass was strong on
security and thin on whether the code computes the right answer. Re-running those
three found **six S2 defects** -- user-visible wrong behavior, including one host
crash. The security conclusions below stand unchanged; the functional verdict did
not.

On the security half: no trust-boundary bypass, secret exposure or
crash-from-hostile-input was found. The seam design holds up under adversarial
reading -- the MCP endpoint, the `exec` tier, the AppleScript and JXA builders,
the capability gate, the Lua callback error path and the release signing flow all
do what the docs say.

## Fixed -- sixth round (six S3/S4s that needed no design call)

Chosen over the three remaining S2s because those each need a decision from the
author and these need none. Two of them share a root cause and one has a date on
it: the next US DST transition is 2026-11-01.

| ID | Fix |
|---|---|
| H-10 | `timer_daily_at` is a self-rescheduling one-shot chain, not a repeating `Timer` with a fixed 86400s interval. A repeating timer can only add a constant, and a calendar day is 23 or 25 hours at a transition, so every daily schedule slipped an hour at the boundary and stayed slipped until relaunch. `Native.nextDailyFire` re-asks the calendar per fire; the chain re-arms BEFORE invoking Lua, so a `stop(id)` from inside the handler cancels the link that is now live. |
| N-4 | usage_stats' 7-day series steps `store.dayAnchors`, which anchors each day at LOCAL NOON -- far enough from either boundary that an hour of shift cannot cross midnight. Read at 23:00 on a 25-hour day the old fixed-second step landed back on the date it had just left, so the widget rendered that date twice and dropped the seventh. `report.lua` already anchored at noon for exactly this reason; this is the same idiom, now shared. |
| H-4 | The daily log writes through `write(contentsOf:)` under `try?`. `FileHandle.write(_:)` is the bridged ObjC method: on a full disk or a revoked descriptor it raises an NSException that Swift cannot catch, so the app aborted -- on the one path every `ctx.log` call takes. The rollover branch also keys on the DAY alone now; keyed on `logHandle == nil`, a failed open re-entered it for every later line, costing a `createDirectory` plus a full-directory `pruneOldLogs` scan per log line. |
| P-10 | `signals`' shared watcher contains each subscriber in its own `pcall` and logs what it swallows. One throwing rule used to abort the emit for every rule after it -- and since `bindOne` advances `matched` only after `fire()` returns, those rules then re-fired on every later emit instead of once per edge. |
| N-13, P-13 | `urls.getDomain` peels userinfo and port, then REJECTS whatever is left if it is not host-shaped, rather than deleting the offending bytes: `host.com:8443` yielded `host.com8443`, `user:pw@sub.host.com` yielded `userpwsub.host.com`, and `[::1]:8080` yielded `18080`. Those strings are persisted, not merely shown -- the `context` column of the user's daily usage CSV and favicon cache filenames. The localhost guard is equality plus a `.localhost` suffix instead of `find`, which had been rejecting `notlocalhost.com`. |

Test shapes, and why each is what it is:

- **H-10 gets a lint, not an assertion.** The bug is in the WIRING -- a correct
  next-fire time handed to a timer that then ignores it -- so
  `testNoSeamCodeHardcodesADayLength` forbids the literal across both source
  trees, with a roster (empty today) for anything that is genuinely a duration.
  Reverting `timerDailyAt` to the repeating form fails it, naming the file, the
  line and the source text. `testDailyTimerFollowsTheCalendarAcrossDST`
  additionally pins the computation: iterated across the 2026-11-01 fall-back in
  a forced `America/New_York` calendar, every fire must land at 07:30 local, and
  a landmark asserts that a fixed 86400s step is still expected to drift there --
  so a fixture that stops crossing the transition fails loudly instead of
  passing for the wrong reason.
- **N-4's regression is in Swift although the defect is in Lua.** It needs a
  timezone that HAS a transition, and only the Swift suite can force one
  (`setenv("TZ", ...)` + `tzset()` reaches the same C library Lua's `os.date`
  reads). It asserts the naive window repeats a date FIRST -- if forcing TZ ever
  silently fails, both lists come back clean and the real assertion would pass
  proving nothing. Mutated: the seven days come back as `10-27 .. 11-01, 11-01`,

- **H-4's raising-write half gets a class lint** -- every labelled `FileHandle`
  write form either throws or cannot fail, so the rule is that no `.write(`
  takes an unlabelled argument. Both scans self-test their classifier against a
  probe string first, since neither has a real hit left in the tree and an empty
  offender list would otherwise be indistinguishable from a dead pattern. The
  once-per-day rollover half is NOT covered: it needs an unwritable logs
  directory, and `Native.logsDir` is a static with no injection point.
- **P-10's probe makes every subscriber count and then throw**, so the assertion
  does not depend on `pairs()`' undefined iteration order -- a bare loop stops at
  whichever one it reaches first, whatever that turns out to be. Contained-but-
  silent is mutated separately, to prove the log assertion is load-bearing.

## Eighth round (the author's calls, 2026-09-04)

The three remaining S2s were put to the author as a decision rather than a
recommendation, since each trades something a user can see. **P-3 was taken;
N-6 and P-2 were deliberately left open.** That is a decision, not a backlog
slip -- do not "helpfully" implement either without asking again.

**P-3 -- fixed.** A parked rule whose id is already taken is now listed under an
ADDRESS of its own (`<id>\1park<n>`), stamped onto the parked entry at park time
and matched back by EXACT equality. Nothing on the Swift side changed: `RuleInfo`
keeps keying on `id`, and the address flows back into `remove`/`specJSON`
unaltered, so the row the user selected is the row the engine acts on.

The first cut of this got two things wrong, and both were caught by review rather
than by the suite -- worth recording, because they are the same defect P-3 is
about, reappearing inside its own fix.

`<n>` was the entry's INDEX, parsed back out at resolve time. But `remove` and
`update` both `table.remove(parked, ..)`, which renumbers every later entry, and
`RulesView.editing` is a value snapshot that is never re-derived from the
refreshed list -- so the UI hands back an address minted before the shift, and it
resolved to a DIFFERENT parked rule. A wrong-row delete, produced by the wrong-row
fix. The counter is now monotonic, never reset (a stale address must MISS, not
land on whoever occupies that number next), and resolution scans for the stamped
token instead of indexing.

The `\1` separator was also written up as making a collision impossible. It does
not: `\1` is legal inside a JSON string, so a user could type one. What makes a
collision harmless is the resolution -- exact equality against a token this module
stamped, with `specs` answered first in both `remove` and `update` -- so the worst
a forged address can do is make a taken-id check say "taken".

`rules.remove` needed no new branch: an address is not a key in `specs`, so it
falls through to the parked lookup on its own. And `rules.update` on an address
REFUSES a spec that keeps the colliding id, naming the problem: forcing
`spec.id = id` there would either write the `\1` address into the user's stored
rule or silently merge the parked copy onto the live one, and a merge nobody asked
for is worse than an error that says what to change.

The row says WHY through `reason`, not through a field of its own. The first cut
added `duplicateId`, which no Swift code decoded -- so the row carried the fact
and displayed nothing. `parkReason` now returns "another rule already uses the id
'X'", and `RuleInfo.unavailableReason` already renders it as the subtitle and the
tooltip. A new field would have needed plumbing to say the same thing, and until
it got that plumbing the user saw the generic "rule is currently unavailable".

Three halves are mutation-proven: reverting the row id turns the "two rows carry
different ids" assertion red; dropping the address resolution from `parkedIndex`
turns the specJSON assertion red; and going back to parse-the-index turns red the
new assertion that an address minted before a removal still names its own rule.

## Verified true

These hold, each with the line that proves it. For a repo about to go public
this list is half the deliverable: it is the part a reader can check.

**MCP endpoint.** Loopback is enforced at the listener through
`requiredLocalEndpoint`, not by a check that could be bypassed
(`McpServer.swift:60-63`). Gate order is Origin, then path, then method, then
token (`:177-188`). POST only; 405 with `Allow` otherwise. Header cap 16 KiB,
body cap 1 MiB, chunked bodies refused (`McpHttp.swift:37-38`). The token is a
v4 UUID minted once and kept stable (`Boot.swift:128-135`). The tool set is

`run_action`, `set_enabled`, `validate_extension`. There is no eval tool.

**`exec` tier.** Absolute executable path required, argv array with no shell in
the loop (`Native+Process.swift:378-395`); NUL bytes rejected in Lua before the
call (`adapter.lua:926`); stdin pinned to `/dev/null` and cwd to `/`
(`:192-193`); 1 MiB per-stream capture ceiling; a 60 s SIGTERM watchdog with a
hard stop behind it; every launch logged with its full argv. A first-party
feature cannot declare it (`feature_capabilities.lua`).

**Script builders.** AppleScript literals go through `escAppleScript`
(`Native+Browser.swift:58`); JXA strings through a JSON-serialized literal
(`:474`); browser names are checked against a fixed set (`:353`); tab and window

`set_appearance` validates its mode (`Native+System.swift:254`). Chromium
launches pass `--app=` and `--profile-directory=` as bound argv entries, never a
shell string (`Native+Browser.swift:322-325`). Every synchronous AppleScript
carries a `with timeout` ceiling (`Native+AppleScript.swift:91`).

**Debug surface.** The Lua eval channel and the `.env` secret seeder are both
inside `#if DEBUG` (`DebugControl.swift:38`, `DevEnv.swift:1`). The seven
`HAMMERDECK_*` environment knobs (`CONTROL_DIR`, `DUMP_CATALOG`, `DUMP_KEYS`,

behavior in a release build.

**Secrets and privacy.** The OpenAI key lives in the login Keychain under
service `com.hammerdeck.secrets` and reaches the request only as a header

system prompt, the selected text and the model name, and nothing else. Password

**Outbound network.** Exactly the four kinds SECURITY.md lists, and no fifth:

**Error containment.** Trigger fires are pcall-wrapped with a failure-streak
alert (`registry.lua:468-480`); start, stop, option-change and extension load are
wrapped (`:165,190,718,1044,1060`); rules load, bind and effect dispatch are
wrapped (`rules.lua:147,295`, `effects.lua:850`). On the Swift side every
callback runs under `lua_pcallk` with the stack reset and the error routed to a

**Capability gate.** A withheld method becomes a raising stub naming the feature,

**Loader and extensions.** The custom searcher sits at position 2 and claims only

**Suite health.** 2439 assertions pass on the vendored 5.4.7 engine, including
